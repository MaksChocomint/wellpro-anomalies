Проект по объему и содержанию соответствует уровню выпускной квалификационной работы. Это не просто демонстрационный скрипт поиска выбросов, а полноценное full-stack приложение с предметной областью, интерфейсом, серверной логикой, базой данных, несколькими режимами работы и исследовательской частью.

- используются реальные промысловые файлы, включая разные кусты и скважины;
- реализованы несколько методов обнаружения аномалий и проведено их сравнение;

- есть WebSocket-режим для live-отображения данных;
- есть локальный режим анализа файла и быстрая сводка по результатам;
- есть тестовые сценарии для проверки разных типов аномалий;
- есть практическое обоснование, почему одиночные методы недостаточны для буровых данных.

Научно-практическая ценность:

- работа показывает, что для буровой телеметрии нельзя ограничиваться одним статистическим методом;
- обоснована необходимость учета физического диапазона, контекста изменения глубины и поведения датчиков;

## 4. Доработанное техническое задание под фактически реализованный проект

### 4.1 Наименование

Разработка веб-приложения для мониторинга буровой телеметрии и выявления аномальных значений датчиков с использованием статистических, частотных и гибридных методов анализа.

### 4.2 Основание для разработки

Основанием является практическое задание по разработке приложения для поиска аномальных значений датчиков буровой установки. В ходе выполнения работы задача была расширена до прототипа системы мониторинга буровой телеметрии, включающего пользовательский интерфейс, backend-обработку, базу данных, real-time режим, локальный анализ файлов и исследование методов обнаружения аномалий.

### 4.3 Цель разработки

Цель разработки - создать удобное веб-приложение, позволяющее инженеру, супервайзеру или оператору буровой установки:

- выбрать буровой объект в иерархии `компания -> месторождение -> куст -> скважина -> буровая`;
- получать и просматривать телеметрические данные по 12 ключевым параметрам бурения;
- анализировать данные в режиме реального времени или через загрузку исторического `.txt`-файла;
- выбирать метод обнаружения аномалий и настраивать окно/порог анализа;
- визуально видеть аномалии на графиках;
- получать уведомления и сводку по найденным событиям;
- сохранять подтвержденные аномалии в базе данных для дальнейшего анализа.

### 4.4 Реальный решенный кейс

В проекте решен кейс анализа буровой телеметрии по историческим TXT-файлам и потоковой симуляции real-time данных. Данные привязаны к конкретным буровым объектам: кустам и скважинам. Пользователь выбирает объект в интерфейсе, после чего backend подбирает соответствующие файлы телеметрии и передает их на frontend через WebSocket как поток данных.

Дополнительно пользователь может загрузить собственный `.txt`-файл с рейсом бурения. Backend парсит файл, применяет выбранный метод анализа, возвращает данные с флагами аномалий, а frontend показывает графики, прогресс анализа и итоговую сводку.

### 4.5 Источники данных

Система работает с буровой телеметрией в табличном TXT-формате:

- первые строки содержат информацию о начале и окончании рейса;
- третья строка содержит заголовки;
- далее идут числовые значения с разделителем табуляции;
- десятичный разделитель - запятая;
- обязательный столбец времени - `Время`;
- поддерживаются кодировки `utf-8`, `utf-8-sig`, `cp1251`, `cp866`.

Для анализа используются 12 ключевых параметров:

| Параметр | Смысл |
| --- | --- |
| `глубина` | глубина скважины |
| `скорость_бурения` | скорость проходки |
| `вес_на_крюке` | вес на крюке |
| `момент_ротора` | момент ротора |
| `обороты_ротора` | обороты ротора |
| `давление_на_входе` | давление на входе |
| `расход_на_входе` | расход на входе |
| `температура_на_выходе` | температура на выходе |
| `уровень_в_емкости` | уровень в емкости |
| `скорость_спо` | скорость спуско-подъемных операций |
| `нагрузка` | нагрузка |
| `дмк` | диаметр/параметр ДМК по данным ГТИ |

### 4.6 Режимы работы

Система должна поддерживать два основных режима.

Real-time режим:

- пользователь выбирает объект бурения;
- frontend открывает WebSocket-соединение `/api/v1/ws`;
- backend выбирает локальные файлы, привязанные к кусту и скважине;
- данные отправляются по одной строке с задержкой, имитируя поток с буровой;
- выбранный метод анализа применяется к каждому параметру;
- frontend отображает текущий поток на графиках и открывает уведомление при обнаружении аномалии.

Локальный режим:

- пользователь загружает `.txt`-файл;
- frontend отправляет файл на endpoint `/api/v1/analyze/file`;
- backend парсит файл и анализирует все строки выбранным методом;
- frontend запускает симуляцию просмотра файла, показывает прогресс и позволяет перейти сразу к итоговой сводке;
- пользователь получает список и распределение аномалий по параметрам.

### 4.7 Методы обнаружения аномалий

Система должна поддерживать четыре метода.

Z-score:

- сравнивает текущее значение со средним и стандартным отклонением в окне;
- хорошо подходит для одиночных резких скачков;
- в буровых данных может давать лишние срабатывания на нормальных переходных режимах.

LOF:

- оценивает локальную плотность точки относительно соседних значений;
- полезен для локальных выбросов в неравномерных данных;
- может быть слишком строгим и пропускать технологически важные события.

FFT:

- анализирует частотную составляющую сигнала;
- полезен для обнаружения высокочастотных пульсаций и колебаний;
- в буровой телеметрии может быть слишком чувствительным и выделять много событий.

AMMAD:

- гибридный метод `Adaptive Multi-Method Anomaly Detection`;
- объединяет Z-score, LOF и FFT;
- учитывает физические пределы параметров;
- учитывает типичные рабочие окна, рассчитанные по реальным данным;
- проверяет контекст активного бурения: если глубина растет, критические каналы не должны долго залипать;
- использует разные веса методов для разных параметров;
- применяет устойчивость срабатывания и cooldown, чтобы не помечать каждую точку длинного аварийного участка.

AMMAD является основным рекомендованным методом для буровых данных, потому что он учитывает не только редкость точки, но и физику процесса.

### 4.8 Обоснование AMMAD по результатам исследования

В исследовании использовались реальные TXT-файлы из `backend/app/data/rig_files`.

Проверенная база:

Это показывает, что метод стал еще менее шумным и лучше подходит для практического интерфейса, где нельзя перегружать пользователя постоянными тревогами.

### 4.9 Требования к backend

Backend должен быть реализован на FastAPI и выполнять следующие функции:

- запуск приложения и создание таблиц БД при старте;
- проверка доступности через `/api/v1/health`;
- парсинг `.txt`-файлов буровой телеметрии;
- фильтрация данных до 12 ключевых параметров;
- применение выбранного метода анализа;
- WebSocket-трансляция real-time потока через `/api/v1/ws`;
- анализ загруженного файла через `/api/v1/analyze/file`;
- предоставление привязок локальных файлов к буровым через `/api/v1/realtime/file-bindings`;
- CRUD API для справочников и сущностей БД;
- сохранение найденных аномалий в БД.

Основные backend-компоненты:

| Компонент | Назначение |
| --- | --- |
| `main.py` | FastAPI-приложение, WebSocket, загрузка файлов, startup |
| `methods.py` | Z-score, LOF, FFT, AMMAD |
| `analysis_utils.py` | состояние анализа, параметры методов, буферы |
| `data_utils.py` | парсинг и фильтрация TXT |
| `rig_data_utils.py` | привязка файлов к кустам и скважинам |
| `api/rest.py` | CRUD endpoints и сохранение аномалий |

Frontend должен быть реализован на Next.js/React и выполнять следующие функции:

- загружать справочники из БД;

- открывать real-time мониторинг выбранной скважины;
- отображать графики по всем доступным параметрам;
- позволять включать/выключать отдельные графики;
- позволять выбрать метод анализа: FFT, Z-score, LOF, AMMAD;
- позволять настраивать окно анализа и порог метода;
- поддерживать загрузку локального `.txt`-файла;
- показывать прогресс обработки файла;
- давать возможность остановить/запустить симуляцию;
- давать возможность сразу перейти к сводке по файлу;
- показывать модальное уведомление об аномалии;
- сохранять найденные аномалии в БД;
- показывать итоговую сводку по 12 параметрам.

Ключевые элементы интерфейса:

- экран выбора объекта с иерархией `компания -> месторождение -> куст -> скважина`;
- панель статуса `нормальная работа / обнаружена аномалия`;
- блок настроек real-time анализа;
- кнопки загрузки файла, запуска/остановки симуляции, перехода к real-time;
- сетка интерактивных графиков Plotly;
- модальное окно аномалий;
- сводка локального анализа.

### 4.11 Требования к базе данных

В системе используется PostgreSQL. База данных должна хранить:

- компании;
- месторождения;
- кусты;
- скважины;
- буровые установки;
- состояния буровых;
- типы датчиков;
- датчики;
- телеметрию;
- методы обнаружения;
- конфигурации методов;
- найденные аномалии.

Основные таблицы:

| Таблица | Назначение |
| --- | --- |
| `companies` | компании |
| `fields` | месторождения |
| `clusters` | кусты |
| `wells` | скважины |
| `rigs` | буровые установки |
| `rig_states` | состояния буровых |
| `sensor_types` | типы датчиков и единицы измерения |
| `sensors` | датчики на буровых |
| `telemetry` | значения датчиков |
| `detection_methods` | методы анализа |
| `method_configs` | настройки методов для буровой |
| `anomalies` | сохраненные аномалии |

Сохранение аномалий должно работать следующим образом:

- frontend отправляет `rig_id`, метод, окно, порог и список найденных точек;
- backend проверяет наличие буровой и метода;
- backend находит или создает конфигурацию метода;
- backend находит датчик по имени параметра;
- backend создает запись телеметрии, если такой точки еще нет;
- backend создает запись аномалии;
- дубликаты по `telemetry_id + method_config_id` не должны сохраняться повторно.

### 4.12 Требования к пользовательскому интерфейсу

Интерфейс должен быть ориентирован на инженерный мониторинг, а не на рекламную страницу. Главный экран после выбора буровой должен сразу показывать рабочие данные и элементы управления.

Требования:

- понятная иерархия выбора буровой;
- крупные и читаемые элементы;
- явное состояние соединения с backend;
- заметное предупреждение при аномалии;
- возможность скрыть повторяющиеся модальные уведомления;
- управление видимостью графиков;
- интерактивные графики с отметками аномалий;
- сводка по параметрам после локального анализа файла;
- удобная настройка метода без перезагрузки страницы.

Фактический интерфейс уже соответствует этим требованиям: пользователь видит не только графики, но и прогресс файла, статус системы, выбранную буровую, настройки метода, сводку и возможность сохранения аномалий.

### 4.13 Требования к надежности

Система должна:

- обрабатывать некорректные файлы без падения интерфейса;
- выдавать понятную ошибку при отсутствии столбца `Время`;
- поддерживать несколько кодировок файлов;
- сбрасывать буферы при смене метода, окна и порога;
- разделять состояние AMMAD между разными потоками/файлами;
- не дублировать сохраненные аномалии в БД;
- сохранять работоспособность при закрытии WebSocket;
- при отсутствии привязанных файлов использовать fallback-файл.

### 4.14 Требования к тестированию

Необходимо проверить:

- корректный парсинг TXT-файлов;
- работу всех методов: Z-score, LOF, FFT, AMMAD;
- real-time WebSocket-трансляцию;
- локальную загрузку файла;
- отображение графиков и аномалий;
- сохранение аномалий в PostgreSQL;
- работу интерфейса выбора буровой;
- поведение на нормальном файле без аномалий;
- поведение на файлах с физическими пределами, статистическими всплесками, залипанием датчиков, FFT-пульсациями и смешанным сценарием.

Для демонстрации должны быть приложены тестовые файлы:

- `ammad_case_00_normal_ok.TXT`;
- `ammad_case_01_physical_limits.TXT`;
- `ammad_case_02_statistical_spikes.TXT`;
- `ammad_case_03_context_stuck_sensor.TXT`;
- `ammad_case_04_fft_oscillations.TXT`;
- `ammad_case_05_mixed_all_types.TXT`.

### 4.15 Критерии приемки

Работа считается выполненной, если:

- приложение запускается локально;
- backend доступен на `http://127.0.0.1:8000`;
- frontend доступен на `http://127.0.0.1:3000`;
- база данных PostgreSQL поднимается через Docker Compose;
- справочники буровых объектов загружаются из БД;
- пользователь может выбрать буровую установку;
- WebSocket-режим передает данные и отображает их на графиках;
- локальный файл успешно анализируется через backend;
- все 4 метода доступны в интерфейсе;
- AMMAD работает как основной гибридный метод;
- найденные аномалии отображаются в интерфейсе;
- пользователь может сохранить аномалии в БД;
- нормальный тестовый файл не дает ложных срабатываний;
- файлы с искусственно внесенными аномалиями дают ожидаемые срабатывания;
- подготовлены отчеты исследования и валидации.

### 4.16 Ограничения текущей версии

Текущая версия является дипломным прототипом и имеет следующие ограничения:

- нет экспертной ручной разметки аварий, поэтому точность нельзя измерить классическими precision/recall;
- внешнее промышленное API WellPro не подключено напрямую, вместо него используются реальные исторические файлы и WebSocket-симуляция потока;
- нет авторизации пользователей;
- нет полноценной системы миграций БД;
- нет промышленного журналирования и мониторинга ошибок;
- нет отдельной роли для подтверждения/отклонения аномалии экспертом.

Эти ограничения не снижают ценность диплома, но их нужно явно обозначить на защите как направления дальнейшего развития.

### 4.17 Возможное развитие

Дальнейшие улучшения:

- подключить реальный API WellPro/SCADA вместо файловой симуляции;
- добавить ручную экспертную разметку и расчет precision/recall;
- добавить роли пользователей и авторизацию;
- добавить Alembic-миграции;
- добавить журнал действий пользователя;
- добавить классификацию аномалий по типам: физическая, статистическая, контекстная, частотная;
- добавить экспорт отчета по рейсу в PDF/Excel;
- добавить подтверждение аномалии инженером и обратную связь для дообучения/калибровки AMMAD.

## 5. Формулировка для диплома

В рамках выпускной квалификационной работы разработано веб-приложение для мониторинга буровой телеметрии и выявления аномальных значений датчиков. Система реализована как клиент-серверное приложение: backend на FastAPI выполняет парсинг данных, применение методов анализа и взаимодействие с PostgreSQL, frontend на Next.js/React обеспечивает выбор буровой установки, настройку метода, визуализацию графиков и работу с уведомлениями.

Особенностью работы является реализация гибридного метода AMMAD, который объединяет статистические, частотные и контекстные признаки. В отличие от одиночных методов Z-score, LOF и FFT, AMMAD учитывает физические пределы параметров, типичные рабочие диапазоны и состояние бурения, например рост глубины при залипании ключевых каналов. Это делает метод более применимым к буровой телеметрии, где одиночный статистический выброс не всегда означает аварию, а длинное плато может быть как нормальным простоем, так и отказом датчика.

Проведенное исследование на реальных буровых файлах показало, что AMMAD не перегружает пользователя лишними тревогами: в сравнительном benchmark он выделяет меньше событий, чем FFT и Z-score, но сохраняет реакцию на физически и контекстно значимые отклонения. Дополнительно созданы тестовые файлы с нормальным режимом и разными классами аномалий, что позволяет наглядно подтвердить корректность работы системы.

Практический результат работы - прототип системы, который может использоваться как основа для модуля мониторинга WellPro: пользователь выбирает буровую, видит поток телеметрии, анализирует данные выбранным методом, получает предупреждения об аномалиях и может сохранять найденные события в базе данных для последующего инженерного анализа.
