# Руководство администратора и разработчика

## WellPro Anomalies

### Назначение документа

Настоящий документ предназначен для администратора, разработчика или технического специалиста, который разворачивает, сопровождает и проверяет дипломный прототип системы WellPro Anomalies. Руководство описывает состав проекта, порядок запуска, структуру каталогов, работу с базой данных, входными файлами и тестовыми материалами.

### Общая структура проекта

Проект состоит из двух основных частей:

- «backend» - серверная логика, методы анализа, модели БД, работа с файлами и WebSocket;
- «frontend» - клиентский интерфейс на Next.js/React.

Также в репозитории присутствуют:

- «docker-compose.yml» - инфраструктура локального запуска «PostgreSQL» и «pgAdmin»;
- «seed.sql» - наполнение базы начальными данными;
- «backend/app/data/rig_files» - исторические TXT-файлы буровой телеметрии;
- «backend/app/data/validation_cases» - подготовленные тестовые кейсы;
- «backend/analysis_results» - исследовательские отчеты и результаты прогонов.

### Ключевые каталоги backend

- «backend/app/main.py» - точка входа FastAPI-приложения;
- «backend/app/api/rest.py» - REST-маршруты для сущностей и сохранения аномалий;
- «backend/app/methods.py» - реализация «Z-score», «LOF», «FFT», «AMMAD»;
- «backend/app/models» - SQLAlchemy-модели;
- «backend/app/utils/data_utils.py» - парсинг и нормализация входных файлов;
- «backend/app/utils/analysis_utils.py» - служебная логика состояния анализа;
- «backend/app/utils/rig_data_utils.py» - привязка исторических файлов к буровым;
- «backend/app/config/ammad_context.json» - контекстные настройки «AMMAD».

### Ключевые каталоги frontend

- «frontend/app/page.tsx» - главная страница приложения;
- «frontend/components» - пользовательские компоненты интерфейса;
- «frontend/hooks/useWebSocket.ts» - работа с потоковым режимом;
- «frontend/utils/api.ts» - REST-доступ к backend;
- «frontend/utils/fileUtils.ts» - загрузка файлов на анализ.

### Требования к окружению

Для локального запуска требуются:

- Python 3.12+ или совместимая версия, поддерживающая зависимости проекта;
- Node.js и npm;
- Docker и Docker Compose для инфраструктуры БД;
- доступ к локальной файловой системе проекта.

### Зависимости backend

В файле «backend/requirements.txt» зафиксированы основные зависимости:

- «fastapi», «uvicorn», «starlette», «websockets»;
- «pandas», «numpy»;
- «sqlalchemy», «asyncpg»;
- «python-dotenv», «python-multipart».

### Зависимости frontend

В файле «frontend/package.json» зафиксированы основные зависимости:

- «next», «react», «react-dom»;
- «axios»;
- «react-plotly.js», «plotly.js-basic-dist»;
- «react-modal», «lucide-react»;
- «papaparse».

### Конфигурация базы данных

В проекте используется «PostgreSQL». Текущая конфигурация разработки предполагает запуск БД в Docker:

- контейнер «fastapi_postgres»;
- порт публикации «5433»;
- отдельный контейнер «pgAdmin» на порту «5050».

Строка подключения задается в «backend/.env» через переменную «DATABASE_URL». В пользовательской поставке рекомендуется хранить параметры подключения во внешнем конфигурационном окружении, а не в репозитории.

### Запуск базы данных

Из корня проекта:

docker compose up -d

После этого поднимаются:

- «PostgreSQL»;
- «pgAdmin».

### Инициализация базы

Таблицы создаются на старте backend через «Base.metadata.create_all». Для наполнения базы начальными справочниками и объектами можно использовать «seed.sql».

Пример порядка действий:

1. запустить контейнер базы;
2. подключиться к БД;
3. выполнить «seed.sql»;
4. запустить backend.

В текущем проекте seed создает:

- компанию;
- месторождения, кусты, скважины, буровые;
- типы датчиков;
- методы анализа;
- конфигурации метода «AMMAD».

### Запуск backend

Из каталога «backend»:

python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload

По умолчанию backend поднимается на «http://127.0.0.1:8000».

### Запуск frontend

Из каталога «frontend»:

npm install
npm run dev

После запуска интерфейс обычно доступен на «http://localhost:3000».

### Порядок первого запуска

Рекомендуемая последовательность:

1. поднять БД через «docker compose up -d»;
2. при необходимости выполнить «seed.sql»;
3. установить зависимости backend и запустить FastAPI;
4. установить зависимости frontend и запустить Next.js;
5. открыть приложение в браузере;
6. проверить стартовый экран и доступность справочников;
7. протестировать локальный анализ файла и WebSocket-поток.

### Работа backend при старте

При запуске backend выполняет несколько действий:

1. создает таблицы в базе;
2. загружает «default.TXT»;
3. сканирует каталог «backend/app/data/rig_files»;
4. формирует привязки «cluster_number + well_name -> список файлов»;
5. делает эти привязки доступными для WebSocket-симуляции.

### Входные данные

Исторические данные находятся в:

- «backend/app/data/rig_files»;
- вложенных каталогах вида «cluster_<номер_куста>_well_<номер_скважины>».

Валидационные тестовые файлы находятся в:

- «backend/app/data/validation_cases».

Парсер поддерживает:

- кодировки «utf-8», «utf-8-sig», «cp1251», «cp866»;
- табуляцию как разделитель;
- десятичную запятую;
- обязательный столбец времени.

### Структура методов анализа

В «backend/app/methods.py» реализованы:

- «z_score»;
- «lof»;
- «fft»;
- «ammad».

«AMMAD» использует дополнительные настройки из «backend/app/config/ammad_context.json», где заданы:

- физические пределы параметров;
- контекстные рабочие окна;
- правила контроля залипания;
- веса составляющих гибридного балла.

### REST API

В текущей версии используются следующие ключевые маршруты:

- «GET /api/v1/health» - проверка доступности сервиса и БД;
- «GET /api/v1/realtime/file-bindings» - привязки исторических файлов;
- «POST /api/v1/analyze/file» - локальный анализ загруженного файла;
- «/api/v1/entities/*» - CRUD-маршруты сущностей;
- «POST /api/v1/entities/anomalies/save-batch» - пакетное сохранение аномалий.

### WebSocket-канал

Потоковый режим доступен через:

/api/v1/ws

При подключении frontend передает:

- «cluster_number»;
- «well_name»;
- «rig_id».

Сервер выбирает подходящий файл, читает строки по очереди и передает значения клиенту с задержкой от 1 до 3 секунд.

### Отладка и диагностика

При сопровождении полезно проверять:

1. доступность БД и корректность «DATABASE_URL»;
2. наличие исторических файлов в ожидаемых каталогах;
3. наличие столбца времени в локально загружаемых файлах;
4. логи backend при анализе и при WebSocket-подключении;
5. соответствие портов frontend и backend;
6. корректность API-адресов в «frontend/utils/api.ts», «frontend/utils/fileUtils.ts» и «frontend/hooks/useWebSocket.ts».

### Типовые проблемы

#### Frontend не получает данные

Проверить:

- запущен ли backend;
- совпадает ли адрес «ws://127.0.0.1:8000/...»;
- существует ли привязка для выбранного куста и скважины;
- не пуст ли каталог соответствующих исторических файлов.

#### Локальный файл не анализируется

Проверить:

- есть ли столбец времени;
- корректно ли определилась кодировка;
- содержит ли файл анализируемые параметры;
- не поврежден ли табличный формат.

#### Не сохраняются аномалии

Проверить:

- существует ли буровая с переданным «rig_id»;
- существует ли метод анализа;
- доступна ли БД;
- не блокируется ли сохранение ограничением уникальности.

### Работа с отчетами и результатами исследований

Каталог «backend/analysis_results» содержит:

- отчеты по исследованию «AMMAD»;
- benchmark-результаты по 15 файлам;
- результаты validation cases;
- статистики по 12 параметрам;
- подготовленные черновики ВКР и сопроводительные документы.

Для воспроизводимости дипломной работы этот каталог следует сохранять вместе с основным кодом проекта.

### Обновление и развитие проекта

Если проект будет дорабатываться, администратору или разработчику стоит учитывать следующие направления:

- внедрение Alembic-миграций;
- внешняя конфигурация адресов API и WebSocket;
- подключение к реальному источнику телеметрии;
- авторизация пользователей;
- подтверждение аномалий инженером;
- экспорт отчетов и журналирование действий.

### Ограничения текущей версии

- Docker Compose описывает только инфраструктуру БД;
- потоковый режим построен на исторических файлах;
- система не содержит production-контура аутентификации;
- нет промышленной интеграции с внешним WellPro API;
- качество методов не подтверждено экспертной разметкой аварий.

### Заключение

Текущая версия WellPro Anomalies представляет собой воспроизводимый дипломный прототип, который можно локально развернуть, проверить на исторических файлах, использовать для демонстрации архитектуры и сравнения методов анализа. Для администратора и разработчика ключевой ценностью проекта является ясная структура кода, разделение frontend/backend/БД и наличие подготовленных исследовательских и тестовых материалов.
